## S1 One render approval (FU-179)

Cause. Only one stills batch exists in the Tea Shop Ad 2 project (`0861bd1f500876f4`), and its history shows no edit between the last
shot add (revision 5) and the batch start 18 minutes later. So the first approved `storyboard_generate` never started a batch: it
failed before any job existed (most likely a stale revision; an argument the schema refuses, such as `what: "stills"`, fails the same
way). The gate showed the plan card before any of the handler's checks ran, the user approved a call that could not run, the result
was an error with no job card ("rendered nothing"), and the model fixed the call and asked again: a second card. An older saved chat
(`draft-1794208995161`) shows the same model passing stale revisions many times, often because it put several edits of one project in
one reply, all with the revision it last saw.

Fix (`backend_service/tools/studio.py`, `studio_gate.py`):
- Before a card, the gate runs the handler's own checks for each render call: schema, scope, input images, the per-owner job cap,
  and for storyboard generate and render the project, its revision, and the batch plan (unknown or locked shots, nothing to
  generate). A call that would be refused gets the reason at once as its tool result (an error card, not "Declined") and is not on
  the card. The model reads the reason and fixes the call; the user sees one card, for a call that can run.
- A repeat of a storyboard render that Chat started and that is still running (same project, kind, shots, force; or project and
  preview for a film) returns that job instead of a second card. Identical calls in one reply make one row; the copies follow its
  decision and then find its job.
- When an earlier call in the same reply edits the same project, the revision is not checked before the card; at run time a
  generate or render whose revision is older only because of this turn's own edits moves to the current revision (`TurnRevisions`).
- `backend_service/agent.py` (not in my list, smallest change): `_declined_tool_call` accepts a ready `StructuredToolOutput` from the
  gate, so a refusal or the running job reaches the model and the app as a normal result.

Tests: `tests/test_chat_studio_once.py` drives the real studio registry, gate, agent loop and a real project store (temp folder);
only the still and clip makers are fakes. Written first and failing 6 of 7 before the fix: the FU-179 sequence (stale revision, then
the right one) made 2 cards, now 1 and it renders; a refused argument and "nothing to generate" make no card; an edit plus generate
in one reply renders; a repeat while the job runs returns that job; two identical calls make one row and one job; a declined first
copy declines the repeat.

## S7 Cost preview on the plan card

`studio_gate.storyboard_estimate` builds, for a `storyboard_generate`, the time per shot (still and clip) and the total from
`storyboard/estimate.py` (one call for the batch, one per shot and kind; models picked by the route's `_project_variant`, so the
same project models and missing-model sentences as the run bar). The card (`StudioPlanCard.tsx`) lists "Time per shot" rows and a
Total, using the run bar's own studio strings for "About {time}", "Time: unknown until the first run" and the Measured / Estimated
badge with its tooltip. Lists stop at 24 shots ("and N more"). The item's peak memory and model names come from the same estimate.
New chat keys (en text, null in the 10 other locales): `studioChat.plan.perShot, shotNumber, shotStill, shotClip, unknownTime,
moreShots, total`. Tests: 4 Python tests in `test_chat_studio_once.py`, 1 vitest in `studioChat.test.tsx`.

Shared files touched for S7: `src/types/chat.ts` and `src/types.ts` (new `StudioPlanEstimate` type and `estimate` on
`StudioPlanItem`; agent B owns `src/types/*`), `src/styles.css` (the estimate block).
