## 2. DFlash 2 (`draft-dflash` vs `draft-dflash2`)

Read in llama.cpp b12387 `common/speculative.cpp`: `draft-dflash` runs every DFlash-family drafter and picks the implementation from the drafter's metadata (`llama_model_dflash_variant`: DFlash, DFlash 2, DSpark, Lilicorr); `draft-dflash2` (and `draft-dspark`) only add a check that the drafter is that variant. The server log of every app run confirms it: `adding speculative implementation 'draft-dflash2'` under `--spec-type draft-dflash`.

**Decision: keep emitting `draft-dflash`** (no metadata reading in the app). `draft-dflash2` is accepted too and now also gets the full block (`--spec-draft-n-max 15`, clamped by llama.cpp to the drafter's block): without it the explicit type drafted 3 tokens and lost a third of its speed.

| DFlash 2 Q8_0 drafter, `draft-dflash` | 39.7 / 40.4 | 5.44 | 78 % (337/430) |

## 3. Native q8_0 / q4_0 KV on llama.cpp

- `NativeStrategy.llama_cpp_cache_flags(bits)`: 8 → `q8_0`, 4 → `q4_0`, anything else f16. Both types are in every llama-server `--help` list, so the existing pre-validation covers them (a binary without them falls back to f16 with a note). Label "Native q8_0" / "Native q4_0".
- `load_model` keeps `cacheBits` 8 / 4 for native when the server runs them, and adds an f16 retry when a quantized native cache fails to start (note: "GGUF startup failed with Native q4_0 cache, so ChaosEngineAI retried with the standard f16 KV cache.").
- Estimate: `estimate_cache_bytes` uses 8.5 / 4.5 bits per element; `compute_cache_preview` applies it only on the llama.cpp lane (MLX keeps f16 whatever `cacheBits` says), so the Fit / memory-check numbers halve / quarter the KV on GGUF.
- UI: a "KV cache type" slider (f16 / q8_0 / q4_0) under Runtime controls, only for a GGUF model on the native strategy (not for TensorFold); bits reset to 0 when the model is not GGUF. New strings `runtime:controls.kvCacheTypeGguf` and `kvCacheTypeGgufHint`, en plus `null` elsewhere.

Qwen3-VL-8B-Instruct Q4_K_M, 32K window, flash attention on, 3 rounds x 2 replies:

| KV | Decode tok/s (6 replies) | Mean | Footprint after load |
|---|---|---|---|
| f16 | 49.2 55.1 58.9 54.7 52.7 51.7 | 53.7 | 4886 MB |
| q8_0 | 62.2 55.6 56.4 50.8 56.2 50.8 | 55.3 | 2728 MB |
| q4_0 | 52.8 52.0 48.6 47.6 54.1 50.8 | 51.0 | 1575 MB |

The footprint drops (2158 and 3311 MB) are exactly what 8.5 and 4.5 bits per element predict for this model's 4608 MiB f16 cache. Speed ratios set in `NATIVE_LLAMA_QUANT_SPEED_RATIO`: q8_0 1.0 (within noise), q4_0 0.95. Fused attention off (`--flash-attn` left at llama.cpp's `auto`) also loaded and ran q8_0 (47 to 50 tok/s), so no flash-attention gate was added. Quality figures (99.5 / 97.0 %) are not measured.

**FP8 KV (`f8_e4m3`).** Not offered anywhere. `_refused_cache_type` turns any `f8_e4m3` cache flag into f16 with "The f8_e4m3 (FP8) KV cache needs an NVIDIA GPU: llama-server stops at load with it on Apple Silicon and the CPU." unless `host_hardware_class().kind == "cuda"`, because `--help` lists it and pre-validation alone would let it through to the Metal abort. Not tested on CUDA (no CUDA here).

## 4. MoE expert cache (design note only, no code)

Not wired: on CUDA it needs a Fit rule, a setting and a planner estimate together, and plumbing without them would have no caller. Flags in b12441 (`llama-server --help`, `docs/moe-cache.md`):

- `-cmoe/--cpu-moe` (all expert weights in host RAM), `-ncmoe/--n-cpu-moe N` (first N layers' experts), `--moe-cache-mib N` (device cache of the most-used host experts for small batches: decode and speculative decoding; default 0, off), `--moe-cache-cpu-share F` (share of misses computed on the CPU instead of uploaded once the cache is full; default 0). Host experts are pinned only with `-lm none|mlock|dio`; with mmap (the default) they are not, and the CPU share then helps more. `scripts/moe-cache-tune.py` (llama.cpp) picks both values in about 6 server starts.

Proposed design for the 4090 session:

1. **Gate:** CUDA host (`host_hardware_class().kind == "cuda"`, discrete, not unified), GGUF with `<arch>.expert_count > 0` (read by `helpers.gguf_layout`), and `--moe-cache-mib` in the binary's `--help`. Never on Apple (unified memory: experts are already "on the device").
2. **Fit rule** (in `helpers.chat_memory.llama_gpu_need`): if dense weights + KV + compute fit in free VRAM but the experts do not, plan `--cpu-moe` plus `--moe-cache-mib = free VRAM - (dense + KV + compute + 1 GB headroom)`, and `--load-mode none` so host experts are pinned. If even the dense part does not fit, keep today's behaviour (llama.cpp `--fit`).
3. **Setting:** one launch preference `moeOffload: "auto" | "off"` (auto applies the rule above), no free-form MiB in the UI at first; `--moe-cache-cpu-share` stays 0 until measured.
4. **Estimate:** the memory planner shows experts in system RAM (`hostGb`) and the cache size on the card, and the decode estimate drops to a measured factor.

Measure on the 4090 before building: a MoE that does not fit 24 GB (e.g. Qwen3.6-35B-A3B Q8_0 or Nemotron 3.5 Lightning 30B-A3B Q8_0): plain `--fit on` vs `-cmoe --moe-cache-mib 12000 -lm none` vs the tune script's pick; tok/s, load time, VRAM and RAM.
