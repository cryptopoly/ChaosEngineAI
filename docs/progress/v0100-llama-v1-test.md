# v0.10.0: llama-server b12387 (llama.cpp 1.0) through the app's engine path

Branch `v0100/llama-v1-test`. Binary under test: `~/.chaosengine/bin/llama-server`, `1.0.0-dev (build 12387, commit a956a852c)`, plus its dylibs. Backends ran from this worktree with `CHAOSENGINE_LLAMA_SERVER` pointing at it (the packaged app passes its staged binary the same way).

## Fixed (2 commits)
- `c2d103a7` llama.cpp 1.0 removed `--no-mmap` (now `error: invalid argument`) in favour of `--load-mode none|mmap|mlock|mmap+mlock|dio|auto`. The app gated the flag on `--help`, so nothing crashed, but on a shared-memory NVIDIA GPU (DGX Spark, GH200) the no-mmap load was silently dropped. Now `--load-mode none` when listed, else `--no-mmap` (older builds, the turbo fork). Test extended.
- `faa6d124` `_llama_server_help_text` cached an empty result when the first `--help` timed out (8 s). Seen live: on the first backend, the first TurboQuant load took 25 s and came back as "Cache type 'turbo3' is not supported", and every later TurboQuant / legacy-alias load in that backend fell back to f16. On a fresh backend the same loads ran on `llama-server-turbo`. Now only a non-empty help text is cached. Not caused by the bump. New test.

Cache-type parser reads `f8_e4m3` correctly from the new help; turbo fork list unchanged (adds `turbo2/3/4`).
Server log line on every start: `W server_setup: security: no API key is set and CORS allows all origins` (app binds 127.0.0.1; harmless now, a hardened-server note).

## Runs (Mac, Metal)
Through the API (port 8930): Llama-3.2-1B Q4_K_M native f16 150 tok/s, load 5.2 s first / 1 s after; Nemotron-3.5-Bolt-E4B Q4_K_M 38.1 tok/s, with its pinned DFlash drafter (`draft-dflash`, n-max 15) 103.7 tok/s on the same code prompt (2.7x); Llama 1B `ngram-mod` 118.8 tok/s; LFM3-1.7B 183 tok/s; Qwen3-VL-8B Q4_K_M 80.5 tok/s (no mmproj on disk, vision not tested). TurboQuant 3-bit on `llama-server-turbo` (Llama 1B) 54.6 tok/s; `rotorquant` and `chaosengine` both load as `turboquant` on the turbo binary. No unknown-flag warnings in any log; every unload left no `llama-server` process. One expected error line with DFlash: `dflash requires ctx_other to be set (this warning is normal during memory fitting)`.
q8_0 / q4_0 / f8_e4m3 KV: the app offers no quantized KV for llama.cpp (native = f16 only), so these ran through `LlamaCppEngine` in-process with only `NativeStrategy.llama_cpp_cache_flags` patched. q8_0 130, q4_0 130 tok/s (1B). **f8_e4m3 aborts llama-server on Metal**, with and without flash attention: `ggml-backend.cpp:1358: pre-allocated tensor (cache_k_l0 (view)) in a buffer (MTL0) that cannot run the operation (SET_ROWS)`. It is in the allowed list, so the app's pre-validation would pass it.
Speed vs older builds, same app path, Llama-3.1-8B Q4_K_M, 300 tokens, interleaved, 2 runs each: f16 33.0/34.2 (b12387) vs 36.1/36.1 (May build) vs 38.1/38.9 (Homebrew b12110); with flash attention f16 37.3/39.6 vs 40.7/42.4 (b12110), q8_0 35.1/35.6 vs 38.4/38.8. b12387 is about 7-12% slower at decode here. Another agent's sd.cpp build was running, so treat as indicative.
No MTP GGUF on disk (Qwen3.8-27B is MLX only here); MTP not run.

## Note for the owner
In a source run the app finds Homebrew's `/opt/homebrew/bin/llama-server` (b12110) first: `_which_with_fallbacks` checks PATH before `~/.chaosengine/bin`, and the Tauri source-mode resolver uses env or PATH only. The b12387 copy in `~/.chaosengine/bin` is used only with `CHAOSENGINE_LLAMA_SERVER` set or without Homebrew's on PATH. Release builds use the staged runtime (b12387).
